我的 Vibe Coding 工作流 ​

半年时间我用 AI 辅助做了十几个小项目，从「生成的代码跑不起来」到「一个周末能上线一个工具」，中间踩的坑大多不是技术问题，而是流程问题。

这篇文章记录我目前固定下来的六步流程。

第一步：先写「完成定义」，再动手 ​

这是最容易被跳过、但收益最大的一步。动手之前我会先用三句话写清楚：

  • 谁用：只有我自己用，还是要给别人用？（决定要不要做登录、要不要考虑多设备）
  • 最小可用是什么：能完成一次完整闭环的最少功能是什么？
  • 什么算做完了：一句可以验证的话，比如「能把一段文字粘贴进去，导出一份 Markdown 文件」

别跳过这一步

我至少有三四个项目是在写到一半时发现「我其实不需要这个功能」，然后全部推倒重来。写三句话只要五分钟。

第二步：让 AI 搭骨架，不要一次写完 ​

我一开始的坏习惯是让 AI「帮我写一个完整的番茄钟应用」。结果通常是得到一个 800 行的单文件，能跑，但完全不敢改。

现在我会拆成三轮：

轮次目标产出
第一轮能跑起来的空壳页面结构 + 假数据
第二轮一条真实数据链路能读能写，忽略样式
第三轮体验打磨加载态、错误态、动效

每一轮结束我都会自己运行一次，确认没问题再进入下一轮。

第三步：把「判断」留给自己 ​

AI 最容易出错的地方不是语法，而是取舍：

  • 用不用第三方库？
  • 状态放组件里还是全局？
  • 这个功能要不要做？

这些问题我不会直接问「你觉得呢」，而是给出约束再让它对比：

我要在纯前端做本地存储，数据量大概几百条。用 IndexedDB 和 localStorage 各自的代价是什么？请用表格对比，不要给建议。

拿到对比之后我自己决定。这样即使后来发现选错了，我也知道为什么错。

第四步：小步提交，方便回滚 ​

用 AI 写代码时，代码变化的速度远快于手写，所以版本控制更重要：

bash
git add -A
git commit -m "feat: 完成粘贴文本解析"
1
2

我喜欢在每次「AI 改完并且我验证通过」之后立刻提交一次。这样当下一轮 AI 把东西改坏时，我可以直接：

bash
git restore .
1

而不是花半小时回忆哪里被改了。

第五步：让 AI 做代码审查 ​

功能做完之后，我会把关键文件丢回去让 AI 审查，但换一种提问方式：

请以代码审查者的身份看这个文件，重点找：1) 边界条件没处理的地方 2) 没有意义的抽象 3) 我可能误解的 API 用法。不要夸奖，直接列问题。

这个提问方式比「帮我优化一下」有用得多，因为后者通常只会得到一些无关痛痒的重命名建议。

第六步：写完立刻写记录 ​

我会在项目刚做完、还记得所有细节的时候写一篇记录，最少包含三件事：

  1. 为什么做这个（真实痛点）
  2. 最花时间的一个技术点
  3. 如果重做，我会怎么做

这个习惯的价值在几个月后才体现出来：当我遇到类似问题时，翻自己的记录比搜索快得多。

常见误区 ​

  • ❌ 把 AI 当搜索引擎：问「怎么做 X」得到的是通用答案，问「在我的代码里怎么改」才有用
  • ❌ 一次改太多：一轮改三个功能，出问题很难定位
  • ❌ 不运行就继续：生成的代码看起来对，实际报错的位置可能离你以为的很远
  • ✅ 把上下文给足：相关文件、错误信息、你的约束，一起给它

总结 ​

如果只留一条建议，那就是：AI 负责写，你负责判断。判断的质量决定了项目能走多远，而判断力只能靠一次次真实地运行、观察、修正来积累。
